# 注释规范

## 分层原则

| 层级 | 风格 | 说明 |
| ---- | ---- | ---- |
| 组件 / 函数 | TSDoc + 阿里风格 | 公开 API 用完整注释，补齐 `@param`、`@returns` 等标签 |
| 类型 / 接口 | 每个字段单独 `/** */` | 方便 IDE 悬浮提示，字段意图要直接写清 |
| 业务逻辑 | 行内注释写 WHY | 只解释原因、边界和取舍，不解释显而易见的代码 |
| 标记 | `TODO` / `FIXME` / `HACK` | 统一大写前缀，方便全局搜索和批量处理 |

核心一句话：公开 API 用 TSDoc 全量注释，业务代码只注释 WHY。

## 通用规则

- 注释统一使用中文。
- 能通过命名表达清楚的内容，优先改命名，不靠注释补救。
- 不写“把 A 赋值给 B”这类重复代码本身的注释。
- 只在业务语义、边界条件、特殊取舍、兼容处理、临时绕行等场景补注释。
- 常见短名/缩写（如 `cfg`、`ctx`、`ref`、`prev`、`next`）必须在定义处补中文语义。

## 组件 / 函数

- 公开导出函数、类方法、组合式函数、组件对外暴露方法，统一使用 TSDoc。
- 至少写清楚功能、入参、返回值；有异常或副作用时补 `@throws` / `@remarks`。
- 参数说明尽量短而准，不重复函数名。
- 内部私有小函数如果只是局部辅助，优先靠命名表达，必要时只补 WHY 注释。

示例：

```ts
/**
 * 获取用户列表
 * @param params 查询条件
 * @returns 用户列表结果
 */
export function getUserList(params: UserListParams) {
  return request.get("/users", { params });
}
```

## 类型 / 接口

- `type` / `interface` 的字段逐个添加 `/** */` 注释。
- 字段注释写业务含义、单位、取值范围、默认值、是否必填、特殊来源。
- 嵌套对象同样逐层补齐，不要只给最外层接口写总注释。

示例：

```ts
export interface UserInfo {
  /** 用户 ID */
  id: number;
  /** 用户昵称 */
  nickname: string;
}
```

## 业务逻辑

- 方法体内注释统一使用中文 `//`。
- 只在需要解释 WHY 时写注释：为什么要提前返回、为什么要降级、为什么要特殊分支处理。
- 避免解释“这行在做什么”，代码本身已经能说明的内容不要重复。
- 对临时方案、兼容逻辑、性能优化、历史包袱，必须明确写出原因。

## 标记

- 统一使用大写前缀：`TODO:`、`FIXME:`、`HACK:`。
- 标记后面尽量补上明确动作、责任人或关联编号，保证可以被全局检索。
- 不要混用 `todo`、`fixme`、`hack` 等大小写变体。
- 不要把普通说明伪装成标记。

## Vue `script setup`

适用于 `.vue` 文件（`<script setup>`），包括 Vue / Admin / UniApp 场景。

- `ref`、`reactive`、`computed` 等响应式定义按类型 / 接口规则补 `/** */` 注释。
- 组件对外暴露的方法、`emit` 触发相关方法、可复用的通用方法，按组件 / 函数规则使用 TSDoc。
- 方法体内如需解释局部逻辑，统一使用中文 `//`，并只写 WHY。
- 页面级私有状态和局部辅助函数，优先靠命名表达，不额外堆砌注释。
