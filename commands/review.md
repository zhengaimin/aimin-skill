# 目标

`/am:review` 用于按 Aimin 规则与阿里风格 review 当前项目代码，输出问题、风险、优化建议与建议改动点。

## 默认行为

1. 先检查当前仓库、技术栈、项目规则与用户指定的 review 范围。
2. 如果用户指定文件、目录、PR、功能点或改动范围，优先 review 指定范围。
3. 如果用户未指定范围，优先 review 当前工作区改动；没有改动时，再根据最近任务上下文和项目热点文件做只读检查。
4. 默认只输出 review 结果，不直接修改文件。
5. 只有用户明确要求“顺手修复”“直接改”“边 review 边改”时，才进入代码修改流程。

## 读取顺序

1. 先看 `AGENTS.md`、`CLAUDE.md`，确认项目级约束。
2. 再按需读取 `.agent/comment.md`、`.agent/naming.md`、`.agent/api.md`、`.agent/index/constants.json`、`.agent/index/utils.json`。
3. 如果识别为 admin / tauri / uni 项目，再读取对应 `.agent/admin/**`、`.agent/tauri/**` 或 `.agent/uni/**`。
4. 项目侧规则缺失时，回退到安装包内 `comment.md`、`naming.md`、`api.md`、`constant.md` 和技术栈模板。
5. 最后读取待 review 的代码、类型、常量、接口、组件和相关测试。

## Review 重点

- **阿里风格注释**：公开 API 是否有 TSDoc，`@param` / `@returns` 是否完整；类型字段是否逐项 `/** */`；业务逻辑是否只注释 WHY；`TODO` / `FIXME` / `HACK` 是否统一前缀。
- **命名与可读性**：是否存在无语义缩写、布尔命名不清、集合命名混乱、函数职责不清、变量名与业务语义不匹配。
- **接口与类型**：请求 / 响应类型是否与 `.agent/api.md` 一致；枚举字段是否引用项目枚举值类型；是否存在无意义空响应类型或 `any` 滥用。
- **常量与枚举**：枚举值是否与后端协议一致；I18N / OPTIONS / CONFIGS 是否覆盖完整；变更是否需要同步索引。
- **业务逻辑**：是否有重复逻辑、过度封装、隐藏副作用、边界缺失、异常处理不一致、临时方案未标记。
- **Vue / Admin 结构**：`script setup` 分组顺序、事件命名、弹窗 / 表格模板、未使用导入变量、页面类型与常量归属是否符合规则。
- **测试与验证**：改动是否缺少必要测试、lint、类型检查或最小验证路径。

## 输出格式

输出必须优先列出发现的问题，并按严重程度排序：

1. **Findings**：问题清单，格式为 `严重级别 - 文件:行 - 问题 - 建议改法`。
2. **Open Questions**：无法从代码确认、但会影响判断的问题；没有则写“无”。
3. **Optimization Suggestions**：不属于缺陷但值得优化的点；没有则写“无”。
4. **Checks**：已执行或建议执行的检查；未执行要说明原因。
5. **Summary**：一句话概括整体质量和主要风险。

## 严重级别

- `Blocker`：会导致功能错误、构建失败、类型严重不匹配或数据风险。
- `Major`：明显违反规则、影响维护性或可能引入线上风险。
- `Minor`：局部可读性、注释、命名、结构问题。
- `Suggestion`：优化建议，不要求立即修改。

## 输出要求

- 没有发现问题时，明确写“未发现必须修改的问题”。
- 每条问题尽量给出文件路径和行号；无法定位行号时说明原因。
- 不要泛泛而谈，必须结合当前代码和规则说明。
- 不要把纯个人偏好写成必须修改项。
- 如果建议修改，要说明改动方向，但默认不直接改文件。
